# Phase 2: search, a command built for agents, and an MCP server

Goal: the history can be searched and cited, and an agent in someone's editor can read the chat and ask a teammate's agent as a tool call, without being taught shell commands in an instructions file.

Depends on: phase 1.

Borrowed from Buzz: answers with receipts, and a command an agent can script. Borrowed from T3 Code: an MCP server for agents the app did not start, read-only unless you say otherwise.

## A. Search on the hub

- [x] **P2-A1** In `src/hub/db.ts`, a contentless FTS5 table keyed by `seq`, holding the text of each `message` and `job.result`. Fill it in the same transaction that stores the event. A `message.edit` from the message's author replaces the original's row; a `message.delete` from the author removes it. Content that does not parse is skipped, never an error. Schema version 6; the hub fills the index from `events` on first start with an empty index, so no fresh database is needed.
- [x] **P2-A2** `GET /search?q=Q&chat=A&limit=N`: `chat` optional, `limit` up to 50. Turn the user's words into a safe FTS5 query by quoting each term, so punctuation cannot be read as query syntax. Apply the same visibility fragment as every other read. Answer `[{ seq, event, snippet }]`, best match first, where `snippet` comes from FTS5's `snippet()` with plain markers the client replaces.
- [x] **P2-A3** `GET /events/{id}` returns one event the caller can see, with its `seq`, or `404`. `GET /events?chat=A&around=S&limit=N` returns a page centred on `seq` S, oldest first.
- [x] **P2-A4** Tests: a word in one channel is found by a member and not by a non-member; an edited message is found by its new words only; a deleted one is not found; `"quotes" AND -odd:syntax` as a query returns results or nothing, never a `500`; `around` returns events on both sides.

## B. Search and links in the window

- [x] **P2-B1** Note links: `player-two://note/<id>`. `src/core/links.ts` makes and parses them. In a message's text, a link is drawn as a chip showing the author and the first words, once the desk has resolved it; a link to a note the reader cannot see is drawn as "a note you cannot see".
- [x] **P2-B2** A `search` command and an `openNote` command in `src/shared/ipc.ts`. `openNote` fetches the event, opens its chat, loads the page around it and tells the window which message to scroll to and highlight.
- [x] **P2-B3** Cmd+K (Ctrl+K on Windows) opens a `Command` dialog: typing filters chats by name at once and, after a short pause, shows search results below them with their snippets. Enter opens the chat or the note.
- [x] **P2-B4** "Copy link" in each message's menu.
- [x] **P2-B5** The window registers itself for the `player-two://` scheme with `app.setAsDefaultProtocolClient`, takes a single-instance lock, and hands a link it is opened with to `openNote`. Only `note` links with a 64-hex id are accepted; anything else is ignored.

## C. The command

Every command below takes `--json`. Add each to the README's Commands table.

- [x] **P2-C1** `player-two search QUERY [--in CHAT]` prints matches with author, time, chat and link.
- [x] **P2-C2** `player-two read ID-or-LINK` prints one note, and with `--thread` its replies.
- [x] **P2-C3** `player-two ask @OWNER/REPO TEXT... [--in CHAT] [--wait SECONDS]`: publishes a `message` tagging that agent, in the direct chat with its owner unless `--in` names a channel, then waits for that one job to end. `--wait` defaults to 900. It prints the result's text, or with `--json` the `job.result` event.

  | Exit | Meaning |
  |---|---|
  | `0` | The agent answered. |
  | `3` | The owner declined. |
  | `4` | The run failed or was stopped. |
  | `5` | Nothing final arrived in time. The last line on standard error is the `player-two read` command that checks later. |

## D. The MCP server

`player-two mcp` is an MCP server on standard input and output. It runs as the person, with their key, and talks to the hub the way the command does. Because it is a local process started by the editor, there is no port and no sign-in page.

Add `@modelcontextprotocol/sdk` as a dependency.

- [x] **P2-D1** `src/mcp/server.ts` and the `mcp` subcommand. Without flags it offers only the reading tools:

  | Tool | Returns |
  |---|---|
  | `whoami` | Name, hub, the repos this person shares. |
  | `list_chats` | Channels joined and people, with unread counts. |
  | `list_agents` | Every agent as `owner/repo` with its branch and whether its owner is here. Optional `query`. |
  | `read_chat` | A page of one chat: `chat`, optional `before`, `limit` up to 50. |
  | `read_note` | One note by id or link, with its replies and the state of any jobs it started. |
  | `search` | As `GET /search`. |

- [x] **P2-D2** With `--allow-send` it adds:

  | `withdraw` | Withdraws a request this person made. |

  A message sent this way is like any sent by the command: a tag in it waits for its target's owner, and that includes a tag of the sender's own agent.

## Notes

- **P2-A1: the index keeps its own copy of the text; a contentless table cannot give a snippet.** Node 26.11.1's `node:sqlite` is SQLite 3.53.4, with FTS5, `snippet()` and `contentless_delete=1`. A contentless table with `contentless_delete=1` takes a delete or an update by rowid without the old text, but `snippet()` on it returns NULL, since it keeps no text to cut one from, and P2-A2 answers with that snippet. So `search` in `src/hub/db.ts` is an ordinary FTS5 table, one column `text`, keyed by `seq` as its rowid, holding a second copy of each message's and answer's text as last edited; an edit is an `UPDATE` and a delete a `DELETE` by rowid. It is filled in `addEvent`, inside the event's transaction. The rules are the fold's (`src/core/chat.ts`), so that search never finds what no reader is shown: an edit or a delete counts only from the message's author, only in the message's own chat (the same author writing to the same recipient), only on a `message` and never on an answer, and an edit after a delete finds no row to change. An edit or a delete naming nothing stored changes nothing, and content its kind does not hold is passed over.
- **P2-A1: how a 0.5 database is let in.** The hub refused any database whose `user_version` was not its own. Now it also opens schema 5, the one it knows how to bring forward, since 6 adds nothing but the index: it lays the index down and fills it from the events, in `seq` order through the same rules, in the transaction that sets `user_version` to 6, so a hub stopped halfway starts over. "On first start with an empty index" is taken as the first start on schema 6, which for a new database fills from no events. Any other version is still refused, and the test of that now expects 6. `protocol.md` says so where it said every other version is refused. The test makes a 0.5 database by dropping the index and setting the version back to 5, which is all that differs.
- **P2-A2: what a query may hold, and the marks.** A word is whatever lies between spaces and control characters; splitting on control characters matters, since a NUL inside a quoted FTS5 string ends FTS5's reading of the query and fails it. Each word is put in double quotes with its own quotes doubled, so FTS5 reads it as a string to tokenize and never as an operator, a column filter, a prefix or a `NEAR` group; one that tokenizes to nothing (`*`, an emoji, a lone quote) matches nothing. A query is at most 8 words, and more is `422 invalid q: Too big: expected array to have <=8 items`, as is one with no words. The task does not ask for a limit, but measured here an FTS5 query costs about 2 ms per word for every 20,000 messages holding it, and 4,000 copies of "the" ran past two minutes, during which `node:sqlite`, being synchronous, leaves the hub answering nobody. `limit` is 20 unless given. The marks are U+0002 and U+0003, plain characters that are not markup a renderer might be tempted to obey; the index replaces either one in a message's text with a space (a separator to the tokenizer, as both already were), so every mark in a snippet is the hub's. A snippet is up to 16 tokens, with `…` where text was cut. `protocol.md` says all of this.
- **P2-A3: the two reads, and the client's calls for all three routes.** `GET /events/{id}` answers `404 there is no event with that id that you can see` both for an id never stored and for one in a chat the caller is not in, so that asking says nothing about a chat one cannot read; a path whose id is not 64 hex digits is no route at all and is `404 Not Found`. Routes again match a pattern, `{id}` being the one parameter, as `{name}` was before P1-B7. `around=S` takes `floor(N/2)` events before S and the rest from S on, in one query, and does not borrow from one side when the other runs short: near either end of a chat the page is short. Together with `before`, or without `chat`, it is `422 invalid query: before or around goes with chat, and after without it`, and the old refusal's words changed to say so. The client's calls went in with this task, since P2-A4's tests use them; each parses with `z.object`, reading past a field a newer hub adds, and the event inside strictly, as every answer does (tested in `test/core.test.ts` with the table of answers, and against the in-process hub in P2-A4):
  - `client.search({ q, chat?, limit? }): Promise<Found[]>`, where `Found` is `{ seq, event, snippet }` and `snippet` is already cut at the hub's marks into `{ text, hit }[]`, so no reader has to know the marks.
  - `client.event(id): Promise<Delivered | null>`, null on the hub's 404. To tell that 404 from any other failure, the transport now throws `Refused`, a `PlayerTwoError` with the HTTP `status`, when the hub refuses; everything that caught a `PlayerTwoError` still does.
  - `client.around({ chat, around, limit? }): Promise<Delivered[]>`, oldest first. Like everything the hub hands over, what these return is untrusted until `client.isTrusted` says otherwise.
- **P2-A4: what the tests hold, beyond the task's list.** In `test/hub.api.test.ts`, each through the client's calls against the in-process hub. Search: a word in a channel is found by both members, best match first (a message saying it three times before one saying it once), in one chat when asked, with every word wanted in any order, and by nobody outside; an edited message by its new words only, a deleted one not at all. The query: 25 inputs, among them `"quotes" AND -odd:syntax`, lone and doubled quotes, `*` and a prefix, `NEAR(…)` with and without a distance, `^`, column filters on the column and on the table's hidden columns, `OR` and `NOT`, a NUL inside a word, emoji, 5,000 characters and an SQL injection, all answered 200 with a list; `"quotes" AND -odd:syntax` finds the message holding those words, a punctuated word is read as its tokens side by side (so `NEAR(retry` wants "near retry"), nine words and no words are 422, and the table is still there afterwards. Removing the quoting fails this test with 500s, and removing `VISIBLE` from the search fails the members' test; both were tried. The reads: one event is answered to both people in its chat, as null to a third and for an id never stored or malformed; `around` is checked in the middle, at both ends, with an odd limit and the default, for someone who cannot see the chat, and with `around` out of place. The index itself, and the upgrade, are P2-A1's test.
- **P2-B1: the links, how the desk looks them up, and how the window draws them.** `src/core/links.ts` exports `noteLink(id): string`, `noteOf(link): string | null`, which takes exactly `player-two://note/` and 64 lowercase hex digits and nothing else, and `notesIn(text): Piece[]`, the text cut into `{ text, note }` pieces, `note` being the id of a link and null for plain text. In running text a link is the prefix and 64 hex digits not followed by another letter or digit, so punctuation after it is fine and a longer run is plain text.
  - The desk: every message and reply in the view carries `notes`, one `NoteView` for each note its text links to that the desk has looked up: `{ state: "seen", id, author, words }`, or `{ state: "hidden", id }`. A note loaded here is read from the fold, edits applied and "message deleted" for a deleted one. Any other is asked of the hub once, through `client.event(id)`, and kept for the session: `null` (the hub's 404) or a signature that fails `isTrusted` makes it hidden, as the chip has no third state; `words` are the first 60 characters on one line, or the kind's name for an event with no text. The answer sends the view again; a hub that could not be reached is asked again the next time the link is drawn. What the hub hid stays hidden until the desk restarts or the user joins a channel from the window, which clears what was kept; a join from the command is not seen. Limit: a note taken from the hub shows its words as first sent, since one event says nothing of a later edit or delete; once its chat is loaded (as P2-B2's `openNote` will), the fold's words win.
  - The window: a link is a chip, a `span` with the link as its title and `data-note` holding the id, showing "author: words", "a note you cannot see", or "a note…" until the desk has looked it up. It is never a link: nothing follows it until P2-B2 and P2-B5 make it open the note. In plain text the pieces from `notesIn` come before tags are picked out. In Markdown, `urlTransform` keeps exactly the note links and hands every other address to react-markdown's `defaultUrlTransform` as before (which turned a `player-two:` address into an empty `href`), an `a` whose address is a note is drawn as the chip whatever its own text, and a remark plugin of a dozen lines makes a link of each note link written out in a text node, so an agent's answer that cites a bare link gets a chip too; code and the text of a link are left alone. The plugin's tree is typed by its own small interface rather than by `mdast`, which is not a dependency of this package. The content security policy and the main process's rule of opening only `http` and `https` are untouched. The smoke test, run under `xvfb-run` in the Playwright image, has bob link to a note alice can see in plain text and in Markdown, and to one she cannot, and finds the three chips and no `player-two` link.
- **P2-B2: the two commands, how the window is told where to look, and the hole a page around leaves.** `search { q }` answers with the reply's new `found`, a list of `{ id, chat, sender, agent, snippet }`, `snippet` the client's pieces as they came; a result whose event fails `isTrusted` is left out, as an untrusted message's text never reaches the window, and the snippet itself is the hub's cut of the text as last edited, which only the event it belongs to is checked for. The hub's 422 for a query of no words or more than eight is said as "a search holds one to eight words". `openNote { id }` tells the window where to look through the view rather than the reply: the open chat's `focus` is `{ id, nth }`, set when a note is opened and cleared when another chat is, `nth` counting the notes opened so the same one opened twice is scrolled to twice; that way a link the main process opens (P2-B5) points the window just as one the window opens does. A note loaded here is found in the fold. Any other is asked of the hub with `client.event`, and opens nothing, with "that link is to a note you cannot see", when the hub answers 404, when its signature fails, when its chat is not in the user's list (a channel they wrote in and left, whose events the hub still shows them), and when the event is not a message or an answer once its page is loaded. "Loads the page around it" alone would leave a hole between that page and the newest page loaded at start-up, which the window would draw as if nothing had been said in between and nothing would ever fill; so after the page around, the desk loads the pages before what it had loaded until it reaches that page, 50 events a request. Whether there is more before is taken from the page around: fewer than half a page before the note means nothing. In the window the chip is a button now, which sends `openNote` and shows the refusal as any failed command is shown; the chat scrolls the focused message to its middle once per `nth`, after its usual jump to the end when a chat is opened, and draws it with a tinted background and ring; a reply opens its thread in the same render so that it is there to scroll to. Tested in `test/hub.test.ts` with a note 100 messages back in another chat: the page around it and everything after it loaded with nothing missing, `focus` set, more before it to load; opened again from another chat with `nth` 2; and a note in a channel bob is not in, one in a channel he left and one never stored refused, the open chat and focus unchanged. Removing the gap filling, or the check that the chat is in the list, fails it.
- **P2-B3: the keys, and what the dialog filters.** Cmd+K and Ctrl+K both open it on every system, as Ctrl+N and Ctrl+B already take either key, so it is Cmd+K on macOS and Ctrl+K elsewhere. It is `Search` in `dialogs.tsx`, in the same modal as the other two dialogs, made wider. cmdk filters nothing itself (`shouldFilter={false}`): the chats are those whose name holds what is typed, at once, and the messages are what the desk's `search` answered for it after 250 ms without typing, best match first, under them; an answer to words that have changed since is dropped, and what was found for the last words stays until the next answer, so the list does not empty with each key. A refusal, such as more than eight words, is a line in the list. Each message shows who wrote it (and which agent, for an answer) and where, and its snippet as spans made from the desk's pieces, the words found in bold in the colour of a tag; nothing is HTML. cmdk picks the first item as the list changes, so Enter opens the first chat that matches, or the best message when none does. In its list Ctrl+N and Ctrl+K move down and up, so the window's own shortcuts now leave alone a key something has already taken; otherwise Ctrl+N in the dialog would have swapped it for the join dialog. The smoke test, under `xvfb-run` in the Playwright image, opens it with Ctrl+K, finds `#history` by "his", finds carol's "the first" in it by those words with both picked out, and with Enter opens `#history` with that message highlighted and inside the visible part of the chat.

- **P2-B5: where a link comes in, what is taken from it, and when the app registers.** The main process takes a link from three places: the arguments it was started with (Windows and Linux), a second copy's arguments through `second-instance`, and `open-url` on macOS. The first two go through `noteIn(argv)` in `src/core/links.ts`, the third through `noteOf(url)`; `noteIn` is the id of the first argument that is exactly a note link as `noteOf` reads it, `player-two://note/` and 64 lowercase hex digits and nothing else, since Chromium may reorder a second copy's arguments and add switches of its own. Every other argument is passed over, a hostile or misshapen link included, so what reaches the desk is only ever `openNote` with an id the command's schema already requires. It is a pure function in core rather than in `src/window/main/main.ts` because that file starts Electron as it loads, which a test cannot import; `test/core.test.ts` holds it to Windows' and Linux's shapes (started by the link, a second copy's arguments with Chromium's switches, an AppImage, a run from source) and to nineteen arguments it refuses: `../` in several places, another host, uppercase hex and scheme, more path, a trailing slash, a query, a fragment, a short or long id, a quote and a switch after the link, the link inside a switch, and other spellings of the scheme. A link waits in the main process until the desk's view is the chat list, loaded, so one the app is started with is opened once there is something to open it in; a second copy, with a link or without, brings the window up, restoring it when minimised. A note the user cannot see is said in the window as the desk words it. `requestSingleInstanceLock` is taken as the main process loads and a second copy quits there, before it starts a desk or a window. `setAsDefaultProtocolClient("player-two")` runs only when `app.isPackaged`: a copy run from its source, as in development and the smoke test, would make the bare Electron binary the system's handler. Not known here: on Linux, Electron registers through `xdg-settings`, which needs a desktop file naming the scheme, and the AppImage has none unless something installs it (electron-builder's `protocols` would write one); on Windows the registry entry it writes, and what a browser hands it, are for the workstation checklist's item on clicking a link. The smoke test starts a second copy of the app with a note link while the first runs: the second quits and the first opens `#history` with that message highlighted. Of the first two runs of that step on this server, both in the same few minutes, the second copy did not quit (once for over a minute, which held the test open, once past 15 s in a bare reproduction), and in 25 runs since, all of it unchanged, it quit within a second every time; why is not found. The step now waits at most 30 seconds, says what the second copy last printed if it has not quit, and kills it when the test ends, so should it happen in CI it fails with that rather than hanging.
- **P2-C3: a withdrawn request exits with 4, and what `ask` takes as the end.** The exit table has no row for a request withdrawn while `ask` waits, which only the asker can do, from the window or another command. It exits with `4`, beside a run that was stopped: the request was stopped before it ran. `ask` stops waiting at the first of answered, declined, failed, stopped or withdrawn, as the fold (`src/core/chat.ts`) moves the job, even though the owner may later run a declined, failed or stopped request again; `player-two read` shows where it stands after that. The waiting, shared with the MCP server's `ask_agent`, is `ask` in `src/desk/notes.ts`: it publishes the message, folds the chat's events from the stream from that message on, and looks at that one job. `--in` names a channel, with or without its `#`, so `--in backend` is `#backend`: a tag in a direct chat with anyone but the owner is one the owner cannot see.
- **P2-D1: what the reading tools hand over, and the SDK.** `@modelcontextprotocol/sdk` 1.32.1, its `McpServer` with each tool's input a `z.strictObject` of zod 4, which the SDK checks before the tool runs and lists as JSON Schema; a refusal, the SDK's own or a tool's, comes back as a result with `isError`. Each tool answers with one JSON text. A note is `{ link, seq, chat, author, agent, at, trusted }`, `agent` being the repo of the agent whose answer it is and `at` an ISO time, and from `read_chat`, `read_note` and `job_status` also `text` as last edited, `edited`, `deleted` and `thread`, the link of the thread it is a reply in. `list_chats` counts unread as the window does, from the newest 50 events of each chat and the read marks the window keeps in `app-state.json`. `read_chat` folds the chat from its page up to the newest, so an edit made since the page counts, and answers `{ notes, before }`, `before` the seq to pass for the page before it and null when there is none; reactions, edits, joins and jobs' events are in what the notes say rather than notes of their own. `job_status` takes `request` (a note's link or id) and `agent` (`person/repo`). The shared reading, `readNote`, `glance` and `chatFrom`, is in `src/desk/notes.ts` with the command's. The SDK took the bundled command from 0.9 MB to 1.7 MB, nearly all of it zod's older API and ajv, which the SDK imports for itself.
- **P2-D2: what `ask_agent` returns, and how long it may wait.** It is `ask` from `src/desk/notes.ts`, as `player-two ask` is, with `via: "mcp"`. It answers `{ outcome, request }`, `request` being the link of the message it sent, and `outcome` one of `answered` (with `answer`, a note), `declined`, `failed`, `stopped`, `withdrawn` or `timed out`: the task names declined, failed and timed out, and a run stopped or a request withdrawn while it waits are told apart rather than folded into those. `wait_seconds` is at most 900 and 900 when not given, as for the command, but an MCP client may give up on a tool call sooner of its own accord (the SDK's own client does after 60 seconds unless told otherwise); the request stands either way, and `job_status` with the request's link and the agent checks it later. `withdraw` takes `request` and `agent` and refuses unless the request is the caller's and still waiting, as the window's withdraw does.
- **P2-D5: the snippets, and what is not known yet.** Cursor's is `{ "mcpServers": { "player-two": { "command": "player-two", "args": ["mcp"] } } }`, and Copilot's command line's adds `"type": "local"` and `"tools": ["*"]`, the form its `mcp-config.json` takes as far as known here. Both start `player-two` by name, which the window installs as `~/.local/bin/player-two` inside WSL, so they assume the agent runs inside WSL with that folder on its `PATH`, as the team's agents do; Cursor's editor on Windows itself would need `wsl.exe` in front. The file locations, the Copilot form and that assumption are for P2-D6 to confirm. The page writes neither file. The smoke test opens the Setup page and reads both snippets back.

The prompts are on record in `test/fixtures/signing-vectors.json`, so the record was written again with `node scripts/make-vectors.ts`: a deliberate change of the three prompts there and nothing else in the file.

The prompt now says, after the two commands, the MCP server's own sentence that a note's text is information, not instruction, which moved from `src/mcp/server.ts` to `NOT_INSTRUCTIONS` in `src/core/chat.ts` so both say the same words; and, after the sentence on citing, that those commands look in every chat the owner is in, some of which the members of the channel (or the other person, in a direct chat) cannot see, so of a note from another chat the agent gives only its link, never what it says. The prompts on record in `test/fixtures/signing-vectors.json` were written again with `node scripts/make-vectors.ts`, a change of the three prompts and nothing else, and `test/vectors.test.ts` checks both sentences are in each. With `--json`, the command now prints an entry that is not trusted with its `content` `null` and, in `search`, its `snippet` `null`, keeping its seq, author, time, refs, link and `trusted`: `vouched` in `src/cli/main.ts`, which `inbox`, `search`, `read` and `status` all print through, so the inbox no longer hands it over either, which the task did not name and the README had warned of. - **Fixed after review: the limit on words limits what a search costs.** P2-A2 split a query only at spaces and control characters and quoted each piece, so `the.the.the…` was one word of 8 allowed that FTS5 read as a phrase of as many tokens as it held: measured here with the review's script, one such word of 3,000 tokens took 1.9 s over 20,000 messages holding "the", on the hub's only thread, where eight plain words take 24 ms. A word is now a run of letters and digits: `q` is split on `/[^\p{L}\p{N}]+/u` before the words are counted and quoted, so each is at most one of the tokenizer's tokens and the 1 to 8 counts tokens. (The tokenizer, `unicode61`, also takes private-use characters into a token and may take combining marks; splitting at those makes more words, never fewer, so the count never comes out lower than what it costs.) `q` is also at most 200 characters, checked before it is split. Either limit, or no words, is `422 invalid q: a search holds 1 to 8 words, in at most 200 characters`, which the window's search says without the `invalid q:`. A query of punctuation or emoji alone, which P2-A2 answered with an empty list, is now that 422, as one of spaces always was; and a punctuated word is no longer a phrase, so `NEAR(retry queue)` finds the message holding "near", "retry" and "queue" apart. Tested in `test/hub.api.test.ts`: the 25 hostile queries are each 200 with a list or 422, never 500, nine words joined by dots are refused and eight are found, and 201 characters are refused where 200 are answered; splitting at spaces again, or dropping the length check, fails it. The README, `protocol.md` and the MCP server's `search` description say so.
