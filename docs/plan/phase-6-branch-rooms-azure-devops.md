# Phase 6: branch rooms, patches, and Azure DevOps

Goal: a branch has a room. In it, an agent can hand over a change as a patch that a person reads and applies with a click, and the branch's pull request and build are in view. The team's code stays on Azure DevOps; Player Two hosts no git.

Depends on: phase 5.

Borrowed from Buzz: the branch is the room, and a patch is a message. Borrowed from T3 Code: Azure DevOps pull requests, looked up and created from the app.

## B. Patches

**Where a run happens.** From this phase, a teammate's request accepted at any mode above `read-only` runs in a throwaway git worktree, so the owner's working tree is never touched by someone else's request. A `read-only` run stays in the checkout itself, so it can see uncommitted work. A request I make of my own agent runs in place, as now.

- [x] **P6-B1** `src/desk/worktree.ts`: `open(checkout, jobId)` runs `git worktree add --detach ~/.player-two/worktrees/<first 12 of jobId> HEAD` and returns its path; `collect(path)` runs `git add -A` then `git diff --cached --binary HEAD` there and returns the diff; `close(path)` removes it with `git worktree remove --force`. On start, the desk removes worktrees left by a crash. Tests against a real temporary repository.
- [x] **P6-B2** The session uses a worktree as above. When accepting, the window says which: "runs on a clean copy of `a1b2c3d`; your uncommitted changes are not included".
- [x] **P6-B3** After such a run, a non-empty diff is published as a `patch` event, referring to the request: the repo as a `RepoRef`, the base commit, the branch, a title (the first line of the agent's answer, cut to 80 characters), and the diff. The same review-or-post choice that governs the answer governs the patch: with review, the owner sees the diff beside the draft and nothing is sent until they send it.
- [x] **P6-B4** A diff over 512,000 characters is not sent. The worktree is kept, the answer says the change was too large to send as a patch, and the owner gets a notice with the path.
- [x] **P6-B5** `src/core/diff.ts`, pure: parse a unified diff into files and hunks for display, and `unsafePaths(diff)` listing any path that is absolute, contains a `..` part, or is inside `.git/`. `touchesInstructions(diff)` lists files an agent would read as instructions: `AGENTS.md`, `CLAUDE.md`, `.cursor/`, `.github/copilot-instructions.md`, `.player-two/`. Tests for each.
- [x] **P6-B6** In the window a patch is a card: title, the files with added and removed line counts, and the diff folded per file, drawn from `diff.ts` as text. No HTML from the diff is ever inserted.
- [x] **P6-B7** "Apply" on the card, for anyone with a checkout of that repo. The desk: refuses if `unsafePaths` is not empty; runs `git apply --check --3way` with the diff on standard input; then asks, with a native dialog that names the repo, the branch the checkout is on, the files, a warning if the tree has uncommitted changes, and a separate warning if `touchesInstructions` is not empty. Only on yes does it run `git apply --3way`. It never passes `--unsafe-paths`. Afterwards it publishes `patch.applied`.
- [x] **P6-B8** "Apply to a new branch": when the base commit exists in the recipient's checkout, create `player-two/<first 8 of the patch id>` from it and apply there, leaving the current branch alone. Offered alongside "Apply".
- [x] **P6-B9** `review` events: "Approve" and "Request changes" with an optional comment on a patch card; shown on the card as who said what.
- [x] **P6-B10** In the two-session scenario: bob asks jacob's agent for a change; jacob accepts at `auto-edits`; the scripted agent writes a file; jacob's own working tree is unchanged; a patch card reaches bob; bob applies it and the file appears in bob's checkout; a patch with a `../` path is refused before git is called.

## C. Azure DevOps

Every call to Azure DevOps is made by the desk, with the person's own token, from inside WSL. The hub never holds a token and never calls Azure.

Things to know before writing it:

- REST base: `https://dev.azure.com/{organisation}/{project}/_apis/…`, with `api-version=7.1` on every call.
- A repo's organisation, project and name come from its key (`dev.azure.com/acme/platform/uploader`), which `src/core/` already derives from every form of the remote.
- **An unauthenticated call answers `203` with a sign-in page, not `401`.** Treat `203`, or any response that is not JSON, as "not signed in".
- The team is behind a proxy that may re-sign TLS. The runtime's Node is started with `--use-env-proxy` and `--use-system-ca` (task P0-H1), so `fetch` honours `HTTPS_PROXY` and `NO_PROXY` and trusts the certificates Ubuntu trusts.

Tasks:

Send it as Basic authentication; if that is answered `203` and the credential came from git, try the same secret once as a Bearer token. Remember which worked for the session. Never log a token.

- **P6-C1: what keeps git from asking, and how a token is sent.** `GIT_TERMINAL_PROMPT=0` alone does not: git still runs an askpass program from `GIT_ASKPASS`, `core.askPass` or `SSH_ASKPASS`, and takes its answer as the credential (tried here, and it did). So `git credential fill` runs with `GIT_ASKPASS` set empty, which git reads as none and which keeps it from the other two, and with `GCM_INTERACTIVE=never`, so Git Credential Manager fails rather than opening a sign-in window while the desk waits. It is asked with `url=` and the repo's https address, so a helper that keys on the path (`credential.useHttpPath`) has it, and its process group is killed when the ten seconds are up, a hung helper with it. A helper that gives a password and no user name makes git ask for one, so it counts as giving nothing. The secret is sent as Basic with an empty user name. The first token found is the one used, as the task orders: one refused does not move the search on. What got a call in is kept, as its whole header, for the life of the `Azure` instance; when a kept one is answered with a sign-in page it is let go, so the next call looks again and finds a token saved meanwhile. Besides `203`, a `401` and a `2xx` whose body is not JSON count as not signed in, and for a token from git each is tried once more as Bearer; a body that is not JSON under any other status is reported with that status, since a proxy's `502` page is not a sign-in problem. `repository` comes in this commit, the one call the authentication needs to be live code; the other calls are P6-C2's, and the tests against a fake server, Bearer included, P6-C3's.
