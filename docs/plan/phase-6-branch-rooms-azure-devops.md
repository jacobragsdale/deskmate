# Phase 6: branch rooms, patches, and Azure DevOps

Goal: a branch has a room. In it, an agent can hand over a change as a patch that a person reads and applies with a click, and the branch's pull request and build are in view. The team's code stays on Azure DevOps; Player Two hosts no git.

Depends on: phase 5.

Borrowed from Buzz: the branch is the room, and a patch is a message. Borrowed from T3 Code: Azure DevOps pull requests, looked up and created from the app.

- [ ] **P6-A1** `channel.pin` carries `branch`: `{ repo, branch }`, where `branch` may be `null` for a room about the whole repo. The hub stores it; `GET /channels` reports it. The `pin` command takes a branch.
- [ ] **P6-A2** The current view for a room pinned to a branch lists who is on that branch, from what everyone advertises: "on this branch: bob, jacob". Members whose checkout is on another branch are listed as elsewhere, with the branch.

It creates a channel named from the repo and branch, cut and cleaned to fit a channel's name with a number added if taken, and pins it. Dismissing a suggestion is remembered in `app-state.json`.
- [ ] **P6-A4** In a branch room the tag list leads with the agents that are on that branch.

## B. Patches

**Where a run happens.** From this phase, a teammate's request accepted at any mode above `read-only` runs in a throwaway git worktree, so the owner's working tree is never touched by someone else's request. A `read-only` run stays in the checkout itself, so it can see uncommitted work. A request I make of my own agent runs in place, as now.

- [x] **P6-B1** `src/desk/worktree.ts`: `open(checkout, jobId)` runs `git worktree add --detach ~/.player-two/worktrees/<first 12 of jobId> HEAD` and returns its path; `collect(path)` runs `git add -A` then `git diff --cached --binary HEAD` there and returns the diff; `close(path)` removes it with `git worktree remove --force`. On start, the desk removes worktrees left by a crash. Tests against a real temporary repository.
- [x] **P6-B2** The session uses a worktree as above. When accepting, the window says which: "runs on a clean copy of `a1b2c3d`; your uncommitted changes are not included".
- [ ] **P6-B3** After such a run, a non-empty diff is published as a `patch` event, referring to the request: the repo as a `RepoRef`, the base commit, the branch, a title (the first line of the agent's answer, cut to 80 characters), and the diff. The same review-or-post choice that governs the answer governs the patch: with review, the owner sees the diff beside the draft and nothing is sent until they send it.
- [ ] **P6-B4** A diff over 512,000 characters is not sent. The worktree is kept, the answer says the change was too large to send as a patch, and the owner gets a notice with the path.
- [x] **P6-B5** `src/core/diff.ts`, pure: parse a unified diff into files and hunks for display, and `unsafePaths(diff)` listing any path that is absolute, contains a `..` part, or is inside `.git/`. `touchesInstructions(diff)` lists files an agent would read as instructions: `AGENTS.md`, `CLAUDE.md`, `.cursor/`, `.github/copilot-instructions.md`, `.player-two/`. Tests for each.
- [ ] **P6-B6** In the window a patch is a card: title, the files with added and removed line counts, and the diff folded per file, drawn from `diff.ts` as text. No HTML from the diff is ever inserted.
- [ ] **P6-B7** "Apply" on the card, for anyone with a checkout of that repo. The desk: refuses if `unsafePaths` is not empty; runs `git apply --check --3way` with the diff on standard input; then asks, with a native dialog that names the repo, the branch the checkout is on, the files, a warning if the tree has uncommitted changes, and a separate warning if `touchesInstructions` is not empty. Only on yes does it run `git apply --3way`. It never passes `--unsafe-paths`. Afterwards it publishes `patch.applied`.
- [ ] **P6-B8** "Apply to a new branch": when the base commit exists in the recipient's checkout, create `player-two/<first 8 of the patch id>` from it and apply there, leaving the current branch alone. Offered alongside "Apply".
- [ ] **P6-B9** `review` events: "Approve" and "Request changes" with an optional comment on a patch card; shown on the card as who said what.
- [ ] **P6-B10** In the two-session scenario: bob asks jacob's agent for a change; jacob accepts at `auto-edits`; the scripted agent writes a file; jacob's own working tree is unchanged; a patch card reaches bob; bob applies it and the file appears in bob's checkout; a patch with a `../` path is refused before git is called.

## C. Azure DevOps

Every call to Azure DevOps is made by the desk, with the person's own token, from inside WSL. The hub never holds a token and never calls Azure.

Things to know before writing it:

- REST base: `https://dev.azure.com/{organisation}/{project}/_apis/…`, with `api-version=7.1` on every call.
- A repo's organisation, project and name come from its key (`dev.azure.com/acme/platform/uploader`), which `src/core/` already derives from every form of the remote.
- **An unauthenticated call answers `203` with a sign-in page, not `401`.** Treat `203`, or any response that is not JSON, as "not signed in".
- The team is behind a proxy that may re-sign TLS. The runtime's Node is started with `--use-env-proxy` and `--use-system-ca` (task P0-H1), so `fetch` honours `HTTPS_PROXY` and `NO_PROXY` and trusts the certificates Ubuntu trusts.

Tasks:

- [x] **P6-C1** `src/desk/azure.ts`: finding a token, in this order: the environment variable `AZURE_DEVOPS_EXT_PAT`; a token saved in `~/.config/player-two/azure.json` (mode `0600`); `git credential fill` for the repo's host and path, with terminal prompts off and a ten-second limit. Send it as Basic authentication; if that is answered `203` and the credential came from git, try the same secret once as a Bearer token. Remember which worked for the session. Never log a token.
- [x] **P6-C2** The calls, each returning parsed data or a problem in words, each with a timeout:

  | Function | Call |
  |---|---|
  | `repository(ref)` | `GET …/_apis/git/repositories/{repo}` for its id, default branch and web address. |
  | `pullRequest(ref, id)` | `GET …/_apis/git/repositories/{repo}/pullrequests/{id}` |
  | `pullRequestsFor(ref, branch)` | `GET …/pullrequests?searchCriteria.sourceRefName=refs/heads/{branch}&searchCriteria.status=all&$top=5` |
  | `latestBuild(ref, branch)` | `GET …/_apis/build/builds?repositoryId={id}&repositoryType=TfsGit&branchName=refs/heads/{branch}&$top=1&queryOrder=queueTimeDescending` |
  | `createPullRequest(ref, { source, target, title, description, draft })` | `POST …/pullrequests` |

  Parse responses with zod schemas that keep only the fields used and ignore the rest: title, status, draft flag, source and target branches, creator's display name, each reviewer's display name and vote, web address; a build's definition name, status, result and web address.
- [x] **P6-C3** `test/azure.test.ts` against a small in-process fake of those routes, with fixtures in `test/fixtures/azure/` written from Microsoft's documented response shapes: each call parses; `203` with HTML is reported as not signed in; a `404` says the repo or pull request was not found; a slow answer times out.
- [x] **P6-C4** A setup check `azure`, skipped when the hub's repos address is not on `dev.azure.com`: a token was found, and `repository` works for one shared repo. Its fix text explains the three ways to supply a token and the scopes a personal access token needs: Code, read and write; Build, read. The setup page has a field that saves a token to `azure.json`.
- [ ] **P6-C5** Pull request references. In a chat whose pinned repo is on Azure DevOps, `!123` in a message is a reference to that repo's pull request 123. In any chat, a pasted pull request address (`https://dev.azure.com/{org}/{project}/_git/{repo}/pullrequest/{id}`) is one too. The desk resolves each once and caches it for a minute; the window draws a chip with the title, the status and the votes, which opens the pull request in the browser. One that cannot be resolved is left as plain text.
- [ ] **P6-C6** A branch room's header shows the branch's pull request (title, status, draft, a summary of votes such as "2 approved, 1 waiting") and its latest build (name and result), each a link. The desk refreshes them every 60 seconds while that room is open and the user is looking. With no pull request it shows "No pull request · Create one".
- [ ] **P6-C7** "Create pull request" in a branch room: a dialog with the title and description filled from the branch's commit subjects (`git log <default>..HEAD --format=%s`), the target set to the repo's default branch, and a draft switch. If the branch is not on the remote or is ahead of it, the desk first asks to run `git push -u origin <branch>`. On success it posts a message in the room with the link.
- [ ] **P6-C8** After "Apply to a new branch", the patch card offers "Push and open a pull request", which is the same flow with the patch's title.
- [ ] **P6-C9** When the latest build for an open branch room changes to failed, the user gets a notice. It is local to each person; nothing is posted to the chat.
- [ ] **P6-C10** **(workstation)** With a real token on a scratch repo: the token is found through git's credential helper inside WSL; a `!` reference and a pasted address both draw chips; the header shows a pull request and a build; a pull request is created. Save one real response of each call, with names removed, over the fixtures written in P6-C3, and fix any schema that does not parse them.

## Notes

- **P6-B5: where a path is read from, and two more names.** `unsafePaths` reads a path wherever `git apply` reads one: the `diff --git` line (both names quoted, or split where the two agree once their first part is gone, as git splits it), `---` and `+++`, and `rename` and `copy` `from` and `to`, each with git's quoting undone, octal bytes included, so `"b/\056\056/x"` is `b/../x`. A hunk's lines are counted from its `@@` line as git counts them: a removed line `-- x` beside an added `++ x` is a `---` and `+++` pair inside the hunk and is not read as a file, and a header placed after a hunk's count has run out is, as git reads it. A path is reported as the diff writes it, `a/` and all. `.git` is matched in any folder and whatever its case, since macOS and Windows file systems take `.GIT` for `.git`. `touchesInstructions` also lists `.cursorrules` (Cursor's older rules file) and anything under `.github/instructions/` (Copilot's instructions for some paths), matches a name in any folder (agents read a nested `AGENTS.md` or `CLAUDE.md` too) and a folder anywhere in the path, without regard to case, and lists a file renamed away from such a name by its old one. Its tests are in `test/diff.test.ts`, held to a diff `git diff --cached --binary HEAD` wrote. For P6-B1: `collect` should pass `--src-prefix=a/ --dst-prefix=b/`, since a user's `diff.noprefix` or `diff.mnemonicPrefix` changes the prefixes, and both `git apply` and the paths drawn here drop the first part of each name.
- **P6-B1: what `open` hands back, what git is pointed at, and what the sweep touches.** `open(checkout, jobId)` refuses an id that is not 64 hex digits, asks for the commit `HEAD` names first and makes the worktree at that commit, so one the owner makes meanwhile does not move it, in a `worktrees` folder it makes with mode `0700`; it returns `{ path, base, gitDir }`, and `collect` and `close` take that rather than the path. `collect` diffs from `base`, not `HEAD`: a run that commits (one at `full` may) would otherwise leave its change out of the diff, and `close` would then throw it away. `gitDir` is the worktree's folder in the checkout's `.git`, read before the run; `collect` and `close` name it with `--git-dir` and `--work-tree` and never follow the worktree's `.git` file, since a run at `auto-edits` may write files but not run commands, and a `.git` it wrote with `core.fsmonitor` set would have the desk run that command at `git add` (the test plants one; plain git runs it). `close` puts back the `.git` file git wrote before `git worktree remove --force`, which refuses a worktree without it. Besides `--src-prefix=a/ --dst-prefix=b/`, `collect` passes `--no-color`, `--no-ext-diff`, `--no-textconv`, `--unified=3` (git apply refuses a patch with no context, which `diff.context=0` would give), `--submodule=short`, `-c core.quotePath=true` and `-c diff.suppressBlankEmpty=false`; the test holds its diff to the same under a configuration that sets each of them otherwise, and under `GIT_DIFF_OPTS`, which beats `--unified`. `git()` in `repos.ts` no longer passes on `GIT_DIFF_OPTS`, nor what `git rev-parse --local-env-vars` lists (`GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE` and the rest), which a git that started the process leaves set and which would send every call to its repository; that holds for its other callers too. git's output is read as UTF-8, so a diff holding U+FFFD, which a byte that is not UTF-8 becomes, is refused rather than sent wrong. `sweep(dev)` runs as the desk starts, before the session: in each checkout under `dev` that has linked worktrees, `git worktree remove --force` for each one there under `~/.player-two/worktrees/` (compared with links followed, as git writes it), and `git worktree prune` when one of those has no folder any more, which also forgets the checkout's other unlocked worktrees whose folders are gone, as `git gc` would. Both leave a locked worktree alone, so P6-B4 can keep one across a restart with `git worktree lock`. The folder is under the home folder, as `protocol.md` has it: `PLAYER_TWO_HOME` does not move it.
- **P6-C1: what keeps git from asking, and how a token is sent.** `GIT_TERMINAL_PROMPT=0` alone does not: git still runs an askpass program from `GIT_ASKPASS`, `core.askPass` or `SSH_ASKPASS`, and takes its answer as the credential (tried here, and it did). So `git credential fill` runs with `GIT_ASKPASS` set empty, which git reads as none and which keeps it from the other two, and with `GCM_INTERACTIVE=never`, so Git Credential Manager fails rather than opening a sign-in window while the desk waits. It is asked with `url=` and the repo's https address, so a helper that keys on the path (`credential.useHttpPath`) has it, and its process group is killed when the ten seconds are up, a hung helper with it. A helper that gives a password and no user name makes git ask for one, so it counts as giving nothing. The secret is sent as Basic with an empty user name. The first token found is the one used, as the task orders: one refused does not move the search on. What got a call in is kept, as its whole header, for the life of the `Azure` instance; when a kept one is answered with a sign-in page it is let go, so the next call looks again and finds a token saved meanwhile. Besides `203`, a `401` and a `2xx` whose body is not JSON count as not signed in, and for a token from git each is tried once more as Bearer; a body that is not JSON under any other status is reported with that status, since a proxy's `502` page is not a sign-in problem. `repository` comes in this commit, the one call the authentication needs to be live code; the other calls are P6-C2's, and the tests against a fake server, Bearer included, P6-C3's. Writing `azure.json` with mode `0600` is the setup page's, P6-C4; reading it does not look at its mode. The tests give git a configuration file of their own (`GIT_CONFIG_GLOBAL`, `GIT_CONFIG_NOSYSTEM`) and `PLAYER_TWO_HOME` a temporary folder.
- **P6-C2: web addresses, what may be missing, and list answers.** Microsoft documents no web address for a pull request (`url` is the REST one, and its `_links` have no `web`), and Builds - List does not say what a build's `_links` hold. So every web address is made from the repo's own (`RepoRef.url`) and an id: a pull request's is `…/_git/{repo}/pullrequest/{id}`, a build's `…/{organisation}/{project}/_build/results?buildId={id}`, and the repository's is its `url`. `isDraft` is in none of Microsoft's samples and is read as `false` when absent, missing `reviewers` as none, a running build's missing `result` as `null`, and an empty repository's missing `defaultBranch` as `null`; branch names lose `refs/heads/`. A list comes as `{ count, value }`, as Microsoft's pull request samples show, although its pages type it as an array. Status, result and vote are passed on as Azure gives them, for the window to word. `latestBuild` asks `repository` for the id each time; nothing is cached. Each call's ten seconds include reading its answer. A 404 says what was not found, "or the token cannot see it", since Azure answers the same for both, and any other refusal carries Azure's own `message`. `Repository`, `PullRequest` and `Build` are typed in `azure.ts`; the view will need them in `src/shared/ipc.ts` when P6-C5 and P6-C6 draw them.
- **P6-C3: where each fixture comes from.** `repository.json`, `pull-requests.json` and `created-pull-request.json` are Microsoft's own samples, whole, from the 7.1 pages of Repositories - Get Repository (by id), Pull Requests - Get Pull Requests ("Pull requests by repository") and Pull Requests - Create. Get Pull Request has no sample at 7.1, so `pull-request.json` is the one pull request of Get Pull Requests' "Just completed pull requests" sample, which is the same `GitPullRequest`. Builds - List has no sample at all, so `builds.json` is written from the `Build` its page documents, with the ids of the repository sample. `sign-in.html` is a short page of the kind Azure answers `203` with, not a recorded one. The fake refuses a call without `api-version=7.1`, answers anything but the two credentials it knows with the sign-in page, and its 404 and 409 bodies are Azure's error shape with TF401019 and TF401179. Besides what the task lists, the tests check each call's path and query and the body of a create, that a token from the environment is never tried as Bearer, that one from git is and that Bearer is then sent first, and the words when no token is found. P6-C10 puts real answers in place of these.
- **P6-C4: the check, the command that saves a token, and what the smoke test leaves untried.** The check comes after `git-auth`. It is skipped when the hub has not said where the team's repos are, when they are not under `dev.azure.com` (the hub reports them as a key, such as `dev.azure.com/acme`), and when no team repo is checked out; otherwise it fails with "no Azure DevOps token was found", or with `repository`'s own words for the first checkout, both with the fix text, and passes saying where the token came from. Finding the token first, to say so, means a token from git is asked of its credential helper twice. The fix text names `~/.profile` for the variable, since the launcher in WSL is a login shell's. The window sends `saveAzureToken { token }`, the one new command; the desk takes it before anyone has joined as well, since the token is the machine's, not an identity's, and `session.ts` leaves it out of the commands it handles, as it does the setup check's. `saveToken` in `azure.ts` trims the token, refuses one with a space inside, makes the config folder `0700` if it is missing, and writes `{ "token": … }` to a file of mode `0600` beside `azure.json`, renamed over it, so no reader sees half a file or one others can read. Nothing sends the token back: the reply is `{ ok: true }` or a problem that does not hold it, and the command schema caps it at 1,000 characters, which the window refuses before the line is written, since a line the desk cannot read is shown to the user as it came. The field is a password field under the check while it fails, emptied once saved. Saving does not run the check again, the user presses "Check again": the smoke test's hub has its repos on `dev.azure.com/acme` and there is nothing to point the window's desk at but the real Azure DevOps, so the test sees the row fail for want of a token with the scopes in its fix, saves one, finds it in `azure.json` with mode `0600` and nowhere in the page, and removes it before the Setup page is opened again. `test/doctor.test.ts` gives git a configuration of its own and fakes the one route the check calls, which `runChecks` reaches through an argument only tests pass; `startHub` takes where the team's repos are, for a hub whose are on GitHub.
- **P6-B2: whose request runs where, what its acceptance says, and what a clean copy does not keep.** A run goes in the checkout when everyone it runs on the say of is the owner: their own message, or an agent's request whose `peopleInvolved` are all them, the test `decide` makes for grants; anyone else's above read-only, under a grant or delegated as well, goes on a clean copy. The copy is named for the run, the sha256 of `runOf(request, repo)`, since one request may tag two of the owner's agents and `open` takes the first 12 of a 64-hex id; so a copy kept from an earlier run of the same request and agent (P6-B4) makes running it again fail to start, saying git's words. Its `job.accepted` names the commit the copy was made at, with `dirty: false`, since the run saw nothing uncommitted and a `±` would say it had. The copy is removed once the run has ended, however it ended, best effort: `sweep` removes what is left when the desk next starts. A run on one keeps no session for a follow-up, since its folder goes, so a reply in its thread starts afresh, and an ask still open when it ends is cancelled with its agent rather than refused. The window says it under the run buttons of anyone else's request, "read-only runs in your checkout; any other mode runs on a clean copy of `a1b2c3d`; your uncommitted changes are not included", with the commit the view's `checkouts` now carry for each, which the desk asks git for at each scan. Tests whose sessions ran a teammate's request above read-only in a checkout of a bare `.git` folder now make a real repository (`checkout` in `test/startHub.ts`), and every test file whose sessions may make a copy gives its process a home of its own (`ownHome`), so that none is ever made in the real `~/.player-two`; the tests of follow-ups run them read-only, in the checkout, and in phase 3's scenario the supervised run writes nothing to bob's checkout.
