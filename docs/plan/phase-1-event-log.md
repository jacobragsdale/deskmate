# Phase 1: one signed event log

Goal: everything that happens is one kind of thing, a signed event with a kind. Notes and status notes go. Approvals become signed records. Later phases add kinds, never a new mechanism.

Depends on: phase 0. Read the "Events", "Kinds", "Jobs" and "After phase 1" parts of [`protocol.md`](protocol.md) first; they are the specification for this phase.

Borrowed from Buzz, which models every action as a signed event in one log.

## What changes

| Today | After |
|---|---|
| A note has a kind of `note` or `status`, an `agent` mark and an `re`. | An event has a `kind`, a `content` string and `refs`. |
| What an agent is doing with a request is a status note whose body is `working\nmain ±`. | `job.*` events with fields. |
| Approving is a click that leaves no record of its own. | `job.accepted` records who allowed which agent to run, for whom, on which branch and commit. |
| Joining, leaving and pinning are calls that change hub tables. | `channel.*` events the hub applies and everyone can see. |
| The hub hands out a note's id, so the sender learns it after sending. | The id is the hash of the signed bytes, known before sending. |
| The client holds a long-poll open. | The hub streams events on one response that stays open. |
| Start-up loads the newest 300 notes across every chat. | Each chat loads its own newest page, and older pages on demand. |

This phase starts a fresh database. Version `0.5.0`, protocol `2`.

## B. The hub

- [x] **P1-B1** Schema version 5 in `src/hub/db.ts`. Drop `notes`. Add:

  ```sql
  CREATE TABLE events (
    seq INTEGER PRIMARY KEY AUTOINCREMENT,
    id TEXT NOT NULL UNIQUE,
    author TEXT NOT NULL,
    recipient TEXT NOT NULL,
    kind TEXT NOT NULL,
    content TEXT NOT NULL,
    ts INTEGER NOT NULL,
    refs TEXT NOT NULL,      -- JSON array
    nonce TEXT NOT NULL,
    sig TEXT NOT NULL,
    chain TEXT NOT NULL
  );
  CREATE INDEX events_by_recipient ON events (recipient, seq);
  CREATE INDEX events_by_author ON events (author, seq);
  CREATE TABLE event_refs (ref TEXT NOT NULL, seq INTEGER NOT NULL, PRIMARY KEY (ref, seq));
  ```

  `members` and `pins` stay; `pins` gains a nullable `branch`.
- [x] **P1-B2** `POST /events`: the four checks in the protocol reference, in that order, each with its own `detail`. Insert, compute `chain`, write `event_refs`, and apply a structural kind, all in one transaction. Answer `201 { seq }`; `409` for an id already stored.
- [x] **P1-B3** Structural kinds: `channel.join` and `channel.leave` change `members`; `channel.pin` checks the author is a member and the repo is under the hub's address, then writes or clears `pins`. An event that fails its structural check is refused, not stored.
- [x] **P1-B4** `GET /events` in its two forms, `chat` with `before`, and `after`. The visibility rule is one SQL fragment used by every read. For a direct chat, `chat=bob` means events between the caller and bob in either direction.
- [x] **P1-B5** `GET /stream?after=S`: `Content-Type: text/event-stream`, first everything visible after S, then each new visible event as it is stored, and a comment line every 20 seconds. Membership is checked when each event is sent, so leaving a channel stops its events on an open stream. Close the response when the client goes away.
- [x] **P1-B6** `GET /audit/head`, and `player-two hub verify`, which walks the table and reports the first `seq` whose `chain` does not follow from the one before.
- [x] **P1-B7** Remove `POST /notes`, `GET /notes`, and the four channel-changing routes. `GET /channels` stays and reports each channel's pinned branch. *(Moved to straight after P1-F2, when nothing calls these routes any more; the branch was done in P1-B3. See Notes.)*
- [x] **P1-B8** In `deploy/k8s.yaml`, on the ingress: a read timeout of an hour and response buffering off for the hub, as annotations for the `nginx` class, with a comment that without them every client's stream drops each minute.
- [x] **P1-B9** `test/hub.api.test.ts`, rewritten for events. It keeps every guarantee the note tests held: only the author can sign, the freshness window, one delivery for a replay, direct events reach two people only, channel events reach members only, leaving stops them, joining reveals earlier ones. - **P1-B2: what the route does where the task leaves it open.** `POST /events` takes the auth header, as the reference's "Auth header" section says every route does but `POST /join`, `GET /healthz` and the downloads; `POST /notes` took none. Whoever signs the request need not be the event's author (from phase 4 a desk posts its agents' events), so the header gates the request and counts as "here", and the four checks are made of the event alone. Each refusal: the envelope `422 invalid <field>: …`, the id `422 invalid id: not the hash of the event's signed bytes`, the signature (or an author nobody joined as) `401 event is not signed by its author`, the time `400 event timestamp is more than 5 minutes off the hub clock; …`, a stored id `409 this event was already stored`, and then `404 nobody named '<to>' has joined`, `403 join <channel> before posting to it`, or `403 <kind> cannot be sent to everyone`: no kind may be sent to `*` until phase 4 names the public ones. The id is looked up before the insert rather than left to the `UNIQUE` constraint, so that a replay is refused at check 3 and not after check 4; nothing can come between the two, as a request is answered in one turn of the loop once its body has arrived. A refused event takes no `seq`. `Database.transaction` is the one place that begins and commits, and `replaceRepos` now uses it too. The note receipt `{ id }` became `noteReceiptSchema`, so that `receiptSchema` is the event's `{ seq }`; it goes with the other note schemas.

That the author of a pin or a leave is in the channel is the fourth check's to refuse, with its `403`. Joining and leaving log the lines the old routes logged. The old pin route stores a `null` branch.
- **P1-B4: the rule and the forms.** The visibility rule is `VISIBLE` in `src/hub/db.ts`, one SQL fragment that `eventsAfter` and `chatEvents` both use and that the stream (P1-B5) reads through, and that search (phase 2) is to use: events to the caller, by the caller, to `*`, and to a channel the caller is in now. Membership is read when the query runs, so leaving hides a channel's history as it did for notes, and joining shows it. A chat is chosen by `chat` (a channel's `#` sent as `%23`); without `before` it starts at the newest. Without `chat` the read is the `after` form, from 0 when `after` is not given. `limit` is 100 unless given, at most 200, for both. `before` without `chat`, or `after` with it, is `422 invalid query: before goes with chat, and after without it`. The protocol reference now says these defaults.
- **P1-B5: how the stream reads, and what its tests can and cannot see.** The stream keeps no events of its own. Each time an event is stored it reads, through `eventsAfter` and so through `VISIBLE`, everything after the last `seq` it has sent, a page of 200 at a time, which is what makes membership count at the moment of sending. When a page comes back short it moves past the newest `seq` in the log, read in the same turn of the loop, so an event the caller could not see as the stream went by is not sent if they later can (after joining a channel, its history comes from `GET /events?chat=`), and a reader in no busy channel does not read the same rows again at every event. It writes only while the response is not waiting to drain, and goes on at `drain`. The headers are flushed at once, so a client knows the stream is open before anything is sent. Its comment line is `:`. The response's `close` clears the ping's interval and takes the stream off the hub's wake-up list. The tests: one runs the hub's `setInterval` on Node's mock timers to see the comment after 20 seconds; one counts the process's active timers through `process.getActiveResourcesInfo()`, one more while the stream is open and back to what it was once the reader hangs up. With the interval left running, that test fails, and the file's process then never exits, so a leak shows as a run that hangs after reporting it. The slow-reader path is not tested: a reader slow enough to fill the socket's buffers would deliver the same events either way.
- **P1-B6: what `hub verify` catches and what it cannot.** It reads `PLAYER_TWO_DB` and nothing else, opens the file read-only, and can run beside a hub that is using it. For each row it works the id out again from the stored fields and the chain value from the one before, so a row changed by hand is named at that row and a row taken out at the one after it. A log rewritten from some row on, ids and chain values and all, still verifies; that is what comparing `GET /audit/head` with a head seen earlier is for. It prints `the chain holds: N events, the last chain value …`, or fails with `the chain breaks at seq S: …` and exits `1`, and says so when there is no file at that path. `/audit/head` takes the auth header like the other routes and answers `{ seq: 0, chain }` with 64 zeros before the first event. The command's `hub` became a function of its own, `hub()`, as one more branch took `run` past the linter's limit, and the README's table of commands has the new line.
- **P1-B8: why the stream drops, more exactly than the task puts it.** ingress-nginx's default read timeout is 60 seconds between two reads from the hub, and the hub writes a comment line every 20 seconds, so that timeout alone would cut a stream only when the hub went quiet. Buffering is what breaks it: nginx holds the hub's writes until its buffer fills, so neither events nor comment lines reach the client, events arrive late, and an idle timeout between nginx and the client (Azure's load balancer's four minutes, or the client's own) ends the connection. Both annotations are there, as the task says, and the comment in the manifest says what each does. Not applied to a cluster.

And P1-D4's rule had no test with two desks of one identity: now one desk sends its own tag from the window while its run is held before acceptance, and the other desk, which sees the `via: "window"` message arrive, starts nothing, then or after the first machine's answer. Starting own tags from what `arrive` brings in fails it.
- **Fixed after review: `hub verify` checks signatures and names a row it cannot read.** It worked out each id and chain value again but never looked at `sig`, which is not part of what the id is the hash of, so a signature changed by hand verified; and a row whose `refs` was not JSON threw `JSON.parse`'s "Unexpected token…" out of the walk instead of naming the row. Now each event's signature is checked against the key its author has in the hub's `users` table, read once at the start, and the first row that fails anything is named with how: `the chain breaks at seq S:` and "that event, or its chain value, is not what was stored after the N before it", "its signature does not hold under the key A joined with", "that row cannot be read as an event (…)", or "its author, A, has no key on this hub to check its signature against". That last one counts as broken, not as passed over: the hub stores no event whose author has not joined and never deletes a key, so a missing key is itself a hand edit. Phase 4's agents, whose keys come from `agent.register` rather than `users`, will need verify to look there too. `parseJson` in `src/hub/db.ts` now gives `undefined` for text that is not JSON, which the row's schema refuses, so every read of a row like that fails as a parse rather than a throw. The README says what verify checks and what still verifies.
- **Fixed after review: every accepted run ends once, whatever the user does when.** Two ways around P1-D3's "exactly one of": quitting with a draft unsent left its job accepted and never ended, and Stop pressed while `describe` was asking git still published `job.accepted`, then spawned the agent only to kill it. On quit the desk now publishes `job.declined` for each draft not sent, as discarding one does, since the draft is lost with the desk in the same way, and its owner can run the request again later; the publishes go out beside the stopped runs' endings, inside the same three seconds, and an answer that comes back for review after quitting began is declined in the same way instead of being kept. A stop seen once git has answered ends the run there: no acceptance, no agent, a notice "Stopped your … agent before it started.", and the request ready to run again. A stop that lands while the acceptance is being published leaves the acceptance standing and ends the run as stopped without starting the agent. `protocol.md` says the desk declines unsent drafts when it quits, and the README lists the decline among the endings. Tested with a draft left unsent at `stop()` and a run whose `describe` is held while it is stopped.
- **Fixed after review: an answer quotes only a request from its own chat.** The fold puts an answer in its request's thread only when the request is in the answer's chat, but the session looked up the request to quote, and the acceptance whose branch and commit an answer's header shows, across every chat it had loaded, so an answer whose `refs[0]` named a message from another chat showed that message's text as its quote, and that chat's run as where it ran. Both now come from `ChatLog.answered`, which looks only in the answer's own chat; an answer to anything else shows no quote and the branch it names itself, as one to a request not loaded does. Tested with alice's answers to bob naming a request in a channel and one in their own chat.
- **Fixed after review: Esc stops every run of the open chat.** The message box's Esc sent `stop` for each running line it found under the chat's top-level messages, so a run on a request made in a reply, whose line is under the reply, ran on. Rather than have the window find the runs in what it draws, Esc now sends one new command, `stopAll { chat }`, and the desk, which holds the runs, stops each one whose request is in that chat, in a thread or not, and none in another. Tested with two runs in one chat, one of them on a reply, and one in another chat.
- **Fixed after review: an agent runs the request as its owner was shown it.** The prompt takes the request's text as last edited (P1-C4, kept), so an edit landing between the owner reading a request and clicking Run changed what the agent was given, and the approval named an id that did not fix the text. Of the two ways out the review offered, refusing such a run was small enough to do, so the README's claim about ids stands: the `run` command now carries `text`, the request as the window drew it (`body`), and the desk refuses the run when the request's text is not that any more, saying who edited it and to read it again; nothing is published and nothing starts. The window's Run buttons send the message's `body`, and the tests run through a helper that sends what the session shows. Tested with an edit that lands after bob read the request: the run with what he saw is refused and starts nothing, and one with the new text runs it. The README says so beside the approval record.
