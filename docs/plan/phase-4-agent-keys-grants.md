# Phase 4: agent keys and standing grants

Goal: an owner can say once, in a signed and expiring record, "bob may ask my uploader agent, read-only", and from then on bob's requests run without a click. And what an agent says is signed by the agent, so a reviewed answer and an unreviewed one are different things cryptographically, not by a flag.

Depends on: phase 3. A grant names a permission mode, and phase 3 is what makes a mode enforceable.

Borrowed from Buzz: an agent has its own key, and its owner signs what it may do.

## The design

**Agent keys.** Each checkout's agent has an Ed25519 key of its own, kept beside the owner's. The owner announces it with an `agent.register` event. From then on, an event whose author is `jacob/uploader` is checked against that key.

**Who signs what.**

| Event | Signed by | Because |
|---|---|---|
| `job.accepted`, `job.declined` | The owner | It is the owner's decision, made by hand or by a grant on their desk. |
| `job.result` posted directly | The agent | Nobody read it first. `reviewed: false`. |
| `job.result` the owner reviewed and sent | The owner | They read it and pressed send. `reviewed: true`. |
| `job.progress`, `job.error`, `job.cancelled` | The agent | The run's own reports. |

**Grants.** A `grant` event from the owner, to everyone:

```ts
{ agent: "jacob/uploader",
  askers: ["bob"],          // names, or "*" for anyone on the hub
  mode: "read-only",        // a permission mode
  delivery: "review" | "post",
  expires: 1800604800,      // Unix seconds; at most 30 days after the event's own time
  runsPerDay: 20 }          // 1 to 1000
```

A request matches a grant when the grant's author owns the agent, the asker is listed, the grant is not revoked, the time is before `expires`, and fewer than `runsPerDay` jobs were accepted under it in the last 24 hours. The count comes from `job.accepted` events in the log, so it survives a restart. The owner's desk decides; the hub does not enforce grants.

**The honest edge.** The agent runs as the owner's operating-system user, so it could read the owner's key file if it went looking. Agent keys make the honest path attributable; they are not a wall between an agent and its owner. The README must say so.

## A. Agent keys

- [x] **P4-A1** `src/desk/agentKeys.ts`: `agentKey(home, repo)` loads `~/.config/player-two/agents/<repo>.key`, creating it with mode `0600` in a `0700` folder if missing.
- [x] **P4-A2** When the session shares a repo for the first time, or finds no `agent.register` of its own for that repo with the current public key, it publishes one to `*`. Replacing the key file and restarting therefore rotates the key.
- [x] **P4-A3** The hub: schema version 7 adds `agents (owner, repo, pubkey, seq)`. `agent.register` is structural: only a person may author it, and it sets the key for `author/repo`, the newest winning.
- [x] **P4-A4** The hub accepts an author of the form `owner/repo` when the signature verifies against that agent's registered key, the owner could write to `to`, and the kind is one an agent may author: `job.progress`, `job.result`, `job.error`, `job.cancelled`. Anything else from an agent is refused with a `detail` that says agents cannot send it. Phase 5 adds `job.request` to the list.
- [x] **P4-A5** The auth header may be signed by an agent: the name is `owner/repo`. Reads then see what the owner sees. Update `caller` in the hub and the header's pattern.
- [x] **P4-A6** Clients learn agent keys from `agent.register` events signed by an owner whose key they have pinned, and check agent-authored events against them. An agent-authored event with no known registration is untrusted. In `src/core/chat.ts`, a `job.*` event from `owner/repo` counts exactly as one from `owner` does, for that repo only.
- [x] **P4-A7** The session signs as in the table above. During a run the agent's process gets `PLAYER_TWO_AGENT=owner/repo` and `PLAYER_TWO_AGENT_KEY_FILE`; the `player-two` command and `player-two mcp` sign with that key when both are set, so anything the agent does through them is the agent's, not the owner's.
- [ ] **P4-A8** Tests: an event signed with the wrong agent key is refused; an agent cannot author a `message`; a reviewed result verifies against the owner's key and an unreviewed one against the agent's; after a rotation the old key is refused and the new one accepted; a client that has never seen the owner treats the agent's events as untrusted.

## B. Grants

- [x] **P4-B1** `grant` and `grant.revoke` in `src/core/kinds.ts`, public kinds. The schema refuses an `expires` more than 30 days after the event's `ts`.
- [x] **P4-B2** `src/core/grants.ts`, pure: `liveGrant(grants, revocations, accepted, { agent, asker, now })` returns the matching grant or nothing. When several match, the one with the lowest mode wins. Tests for each condition: wrong asker, `*`, revoked, expired, the daily count reached, and the count freeing up after 24 hours.
- [ ] **P4-B3** The session keeps grants and revocations from the log (they are public, so `catchUp` brings them). When a request for one of my agents arrives and a grant matches, it accepts with `by: { grant: id }`, the grant's mode and its delivery, with no command from the window. If the agent cannot honour the grant's mode it does nothing and the request waits for a click as before, with one notice saying why.
- [ ] **P4-B4** A request sent by the command, by MCP or by a workflow can run under a grant like any other. A request for my own agent never needs one.
- [ ] **P4-B5** Commands `grant` and `revoke` in `src/shared/ipc.ts`.
- [ ] **P4-B6** Tests in the two-session scenario: jacob grants bob `read-only` with review on `uploader`; bob's next request is accepted with nobody touching jacob's session and a draft appears for jacob; with `delivery: "post"` the answer is posted, signed by the agent; a write attempt in that run is refused; jacob revokes and the next request waits; a grant for carol does nothing for bob; advancing the clock past `expires` ends it.

## C. The window

## Notes

- **P4-B1: the 30-day limit needs the event's time, and what is left for the hub and the publisher.** The `grant` member of `contentSchema` is read from `{ kind, content, ts }`, and `readContent` passes the event's `ts`, so a grant lasting longer than `MAX_GRANT` is read as unknown by every reader. `Client.publish` in `src/desk/client.ts` still parses `{ kind, content }`, so publishing a grant fails there until the task that first publishes one (P4-B5) parses it with the `ts` it signs with. `PUBLIC_KINDS` in `src/core/kinds.ts` names the kinds that may be sent to `*`. The hub does not read it yet: `mayWrite` in `src/hub/app.ts` refuses `to: "*"` for every kind, so a grant cannot be posted until it accepts `*` for exactly these kinds (and `agent.register`, which P4-A3 adds to the set); and `ChatLog.add` in `src/core/chat.ts` still passes over every event to `*`, which suits P4-B3, where the session keeps grants apart from the chats. Both were left because this was built on a branch that did not touch the hub or the chat fold.
- **P4-B2: what `liveGrant` reads, how a tie is broken, and what P4-B3 and P5-A5 change in it.** It takes the log's entries, so one whose signature does not hold counts for nothing, and returns the grant's content with its event's `id`. A revocation counts only from the grant's author, and so does an acceptance: anyone else's `job.accepted` naming the grant would otherwise spend its runs. The plan says the lowest mode wins and leaves a tie open: at one mode, review wins over posting directly, as it allows less, and then the grant first in the log by `seq`. The order of modes is `MODES` in `src/core/wire.ts`, the order `atMost` uses, since the core cannot import `src/desk/permissions.ts`. `job.accepted`'s `by` cannot hold a grant yet, and phase 3 is changing that schema's `mode` on `main` at the same time, so `liveGrant` reads `by.grant` from an acceptance with a small schema of its own, `underSchema`; when P4-B3 lets `by` hold `{ grant: id }` in `src/core/kinds.ts`, it should read acceptances with `readContent` and delete `underSchema`. For P5-A5, the request's `asker` becomes the people involved and the one call to `covers` becomes `people.every(...)`.
- **P4-A3: done before P4-A2, and what it settles for the public kinds.** P4-A2's session publishes `agent.register` to `*`, which the hub refused until this task, so this one was committed first. `mayWrite` in `src/hub/app.ts` now lets anyone send to `*` exactly the kinds in `PUBLIC_KINDS` (`agent.register`, `grant`, `grant.revoke`), and still refuses every other kind there with the words it used before; the hub reads nothing of a grant. `agent.register` is structural and must be sent to `*`, or it is refused with 422 and not stored, so every reader can learn the key from it; content that is not `{ repo, pubkey }` (a key in lowercase hex) is refused as any structural kind's is. The event is stored first and acted on after, in the same transaction, since the `agents` row keeps the registration's `seq`; a refusal still stores nothing. That only a person may author it is P4-A4's: until then no agent can author anything. Schema 7 is schema 6 and the `agents` table, so a database phase 2 made is brought forward by laying the table down empty: a hub of schema 6 refused every event to `*`, so it holds no registration to learn from. Schema 5 still gains the search index as before, and then the table. `Client.publish` reads the content it signs with the `ts` it signs it with, so a grant can be published (P4-B5): one lasting more than 30 days is refused before it is signed.
- **P4-A2: how the session knows what it registered, and a race it uncovered.** The events to everyone are in no chat, and catching up from the start would read the whole log, so `GET /events` takes `chat=*` for them, paged like any chat (`protocol.md` says so). `Client.registeredKey(agent)` reads them, newest first, back to the newest it read before, and keeps each `agent.register` with whether it holds under the key pinned for its author; the key is the one in the newest of those that holds, sent to `*`. The task says to register when no registration of mine has the current key; the session asks instead whether the newest one has it, since a key file restored after a rotation would otherwise stay unregistered while the hub holds the other key. It asks once for each checkout in each run of the session, in `share()`, before the checkout is offered to run, so a key file replaced while the desk runs counts from its next start, as the task says; a registration that cannot be published fails the share like an advert that cannot, and is tried again on the next beat. One identity on two machines with the same repo makes two keys, and the newest registration wins, so only the last desk to start has an agent that can sign: copy `agents/<repo>.key` with `key`. Registering made a session's first share slower, which uncovered a race in `joinChannel`: it loaded the channel's page before the stream's starting point was read, so a message stored between the two was in neither, and the channel test lost one. A channel joined before the stream is followed is now left to the first pages loaded after that point is fixed, which take it in with every other chat.
- **P4-A4: the protocol goes to 3, and what the hub's reads and `hub verify` make of an agent.** An event's `author` may now be `owner/repo` (`AUTHOR` in `src/core/wire.ts`, with `isAgent` and `ownerOf`), and a client of protocol 2 parses the envelope strictly, so one page holding an agent's event would fail it whole and that client could load nothing. That is the hub and its clients having to be updated together, so `PROTOCOL` is 3, and an older desk is told to update by the hub's `/info` instead of failing on its first agent event; the versions table in `protocol.md` has the row, and the package's version is left for whoever cuts the release. The hub checks an agent's signature against its owner's newest registration, and refuses one with none as it refuses an unknown person, in the same words. Which kinds an agent may author is `AGENT_KINDS` in `src/core/kinds.ts`, checked first in `mayWrite` so the words say agents cannot send it (`agents cannot send message: only a person can`), whatever it was sent to; then the owner must be able to write there, a channel the owner is in, a person who has joined. The reads count an agent's events as its owner's: what a caller sees includes what their agents wrote, and a direct chat holds what either person or their agents wrote to the other (`byPerson` in `src/hub/db.ts`, a `GLOB` on `owner/*`, which no character of a name can widen). `hub verify` checks an agent's event against the key its owner had registered for it at that point in the log, learning each registration as it walks past it, so an event signed with the key a rotation replaced, put in by hand with its chain value made good, is named at its row.
- **P4-A5: what an agent's header may do beyond reading.** The header's pattern is the author's, `AUTHOR` in `src/core/wire.ts`: `authClaim` now refuses any other name, which before it left to the lookup. The signed text is unchanged, so the signing vectors are too. `caller` checks the header against the key the name signs with, as an event is checked, and a route is handed both the owner, `me`, which every read goes by, and who signed, `signer`. Posting an event needs nothing more, since the event's own signature decides. `PUT /repos` is refused to an agent, which would otherwise replace what its owner shares, and an agent's request does not mark its owner as seen: an agent at work under a grant says nothing of whether its owner is at their desk. Neither is in the task; both keep an agent's key from doing more than reading as its owner and posting its own reports.
- **P4-A6: an agent's key as of its event's place in the log, and what the reader shows of an agent's events.** `Client.isTrusted` now takes the event with its `seq`. An agent's event is checked against the key in its owner's newest registration before that `seq`, among the registrations that hold under the owner's pinned key, not against the newest registration of all: after a rotation an answer signed before it still holds, and one signed with the replaced key after it does not. Agents' keys are not pinned in `known.json`, since a rotation must replace them; what pins them is the owner's key, which is pinned as before, the first time anything of theirs is checked, a registration included, and `protocol.md`'s table says so. "A client that has never seen the owner" is taken as one with no registration from the owner it can believe: there is none, or the owner's pinned key is not the one that signed it. A client learns a registration as it checks one, from the stream or a page, and asks the hub for those it has not read only when an agent's event does not hold under what it knows: the security is the same as asking every time, since a hub that withheld a rotation could do so either way, and an agent's report every ten seconds does not cost a request each. In the fold, anything from an agent but a report of its own run about its own repo counts for nothing, so its message tags nothing and its answer about another repo is shown nowhere; a report that counts counts exactly as its owner's, `chatOf` puts it in its owner's chat, and an answer from my own agent is neither unread nor rings for me. The session shows an agent's answer, a note's author and a search hit under the owner's name, as before agents signed (`agent` says it is the agent's), and the command line does the same; P4-C4 adds what the signer says. The MCP server's `author` stays who signed it, beside `agent`. A warning about an event whose signature fails names the author it claims.
- **P4-A7: how a run is told who it is, and what the command does with it.** A `Client` has a `signer`, the person or with `as(agent, key)` one of their agents, which signs its events and its auth headers, while `config.name` stays the person, so everything that reads as "me" reads as the owner. The session signs `job.accepted`, `job.declined` and a reviewed `job.result` as the owner, and a run's `job.progress`, `job.error`, `job.cancelled` and an answer posted with nobody reviewing it as the agent, with the key it registered this run; an answer that cannot be posted is kept as a draft as before, to go out reviewed under the owner's name. `agentEnv` in `src/desk/agentKeys.ts` is what a run is told: `PLAYER_TWO_AGENT=owner/repo` and `PLAYER_TWO_AGENT_KEY_FILE`, the path of `agents/<repo>.key`. Each runner's `run` takes it last: the one-shot command's process and the ACP agent's are started with it added to the desk's environment, and the MCP server a run over ACP is given carries it as that server's `env`, so it signs as the agent whether or not the agent passes its own environment on. A session kept for a follow-up was started for one repo, which its key names, so it was started with the same. `loadClient` takes an environment: the command and `player-two mcp` pass their own, the desk and the setup check none, so neither of those ever signs as an agent. With both set it signs as that agent, after checking it is one of the identity's own, and with one of them it is the person. Signing as the agent changes nothing that agent may do through the command but what it signs: reads see what its owner sees, and `send`, `ask`, `channel join` and MCP's sending tools are refused by the hub, as an agent may not send a message or join a channel (phase 5 gives it `job.request`). The key file is readable by the owner's user, which the agent runs as: that is the honest edge, and the environment names a file the agent could find anyway, the agent's own key and not its owner's.
